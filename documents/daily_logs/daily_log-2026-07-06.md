## 2. Architecture Discussion — Guest Graph Links (Loom-Style)

### Problem

The existing sharing flows require the recipient to have a CortexDrive account (Clerk user). For sharing with recruiters, hiring managers, or external evaluators who have never heard of CortexDrive, this is a hard wall. The Loom analogy: a recruiter receives a Loom link, clicks it, watches the video — no account needed.

CortexDrive needs the same: a shareable public URL that shows the knowledge graph canvas, read-only, no sign-in required.

### What is NOT a fit for this use case

The existing `/discovery?share=<hmac>` single-node guest link is limited to one node and a static text view. It does not render the force-directed graph. It is the right tool for sharing a single entity (a project, an episode) but wrong for sharing a full career graph or cross-domain view with a hiring audience.

### Chosen Architecture — Public Token-Based Graph Link

**Token format:** 256-bit URL-safe random string (`crypto.randomBytes(32).toString('base64url')`). Not HMAC — no content integrity check needed because the token IS the key. The set of nodes is stored server-side; the token retrieves it.

**Storage:** New table `graph_share_links` in `cortexdrive_app`:
```sql
CREATE TABLE graph_share_links (
    link_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    share_token     TEXT NOT NULL UNIQUE,
    node_ids        UUID[] NOT NULL,      -- frozen at share time (the canvas snapshot)
    title           TEXT,                 -- e.g., "Sangeetha Career Graph — Q3 2026"
    owner_sub       TEXT NOT NULL,
    org_id          TEXT NOT NULL,
    expires_at      TIMESTAMPTZ,          -- NULL = never expires
    revoked_at      TIMESTAMPTZ,          -- NULL = active
    view_count      INTEGER NOT NULL DEFAULT 0,
    last_viewed_at  TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON graph_share_links (share_token) WHERE revoked_at IS NULL;
CREATE INDEX ON graph_share_links (owner_sub);
```

**Key design decisions:**

| Decision | Rationale |
|---|---|
| Node IDs frozen at share time | Like a Loom recording — the graph state at the moment you clicked "Share" is what the recipient sees. Nodes added after the link is created are not included. |
| Node content is live | When the link is accessed, Neo4j is queried by those frozen UUIDs. Updated descriptions, chunks, and links are shown live. Only the node set is frozen, not the data. |
| No Permify tuples written | The token IS the authorization. No anonymous user concept in Permify. Simpler — no tuple cleanup needed when a link is revoked. |
| No Clerk required | Recipient clicks, sees graph. The "Open in CortexDrive" CTA is the conversion funnel, not a gate. |
| Rate limiting per token | Prevents scraping. 100 requests/hour per token is a reasonable starting limit. |

**The Loom analogy:**

| Loom | CortexDrive Graph Link |
|---|---|
| Video recording at a point in time | Frozen node set at time of "Share" click |
| Always shows the recording | Shows frozen nodes, live node content |
| Public link, no account | Public link, no account |
| View count | View count (for creator to see interest) |
| Revoke link anytime | Revoke endpoint |
| Link expiry | Optional expiry |
| "Sign up to create your own" CTA | "Open in CortexDrive to explore further" CTA |

**What the recipient sees** — `/graph-view/[token]` (new public Next.js route, no Clerk middleware):
- Full interactive force-directed graph visualization (same D3 canvas as dashboard, read-only)
- Click any node → read-only detail drawer (Bento-style: name, type, description, links)
- Header: "Shared by [owner display name]" + creation date
- No chat input, no query bar, no write actions
- "Open in CortexDrive →" button (takes to /sign-in)

**Gateway endpoints:**
```
POST   /api/share/graph-link        — authenticated; creates link; returns { shareUrl, linkId }
GET    /api/share/graph-link/:token — PUBLIC (no auth); validates; fetches nodes from Neo4j; returns graph data
DELETE /api/share/graph-link/:linkId — authenticated; sets revoked_at
GET    /api/share/graph-links       — authenticated; lists links owned by this user
```

**Share URL:** `https://app.cortex-drive.com/graph-view/<token>`

**Who creates the link:** The "Share Graph" button in the canvas toolbar gets a new tab in `GraphShareModal`: "Public Link" tab. Generates on click. Copyable. Shows view count on subsequent opens.

## 3. Architecture Discussion — Clerk Webhook Reliability and the Pull Model

### Problem

For Option B (invite + deferred grant — share with someone who doesn't have a CortexDrive account yet), the design is:
1. Share attempt → user not found in Clerk → store `pending_email` in `share_grants`
2. Send recipient an email (Clerk invite or transactional email)
3. Recipient clicks, creates Clerk account
4. Clerk fires `user.created` webhook → CortexDrive provisions the Permify tuples

**The reliability problem:** If CortexDrive (Cloud Run) is down when the webhook fires, the webhook fails. Clerk retries but only for a limited window. If all retries fail, the pending grant is never provisioned, and the user logs in to find no access — invisible failure.

**The cost constraint:** CortexDrive is a startup running Cloud Run services on a need-only basis (scale-to-zero). The gateway is not guaranteed to be up at any arbitrary moment. Assuming always-on would incur unnecessary compute cost.

### Decision: Pull Model on Login (Primary); Webhook as Optional Fast-Path Later

The pull model is more reliable at startup scale and incurs zero additional infrastructure cost.

**How the pull model works:**

```
Share with alice@example.com (not in Clerk):
  → INSERT share_grants (pending_email='alice@example.com', status='pending', user_sub=NULL, ...)
  → Send notification email: "Sangeetha shared a knowledge graph with you. Sign in at [link] to view it."

Alice clicks link → signs up for Clerk → creates account

Alice's first authenticated request to the gateway:
  → Gateway extracts email from Clerk JWT (or re-resolves via Clerk API)
  → SELECT 1 FROM share_grants WHERE pending_email = $email AND status = 'pending' LIMIT 1
  → Found → run grant activation (async after response):
       - Write Permify tuples for all child_node_ids in each pending grant
       - UPDATE share_grants SET user_sub = $sub, status = 'active', pending_email = NULL
       - redis.del(`perm:${sub}`)
  → Alice's next graph query: tuples exist, access is granted
```

**Why this is correct for the startup phase:**
- Cold start on Cloud Run is 2–3 seconds. The webhook retry window is minutes to hours. But CortexDrive is never down for that long — it's scale-to-zero, not taken offline. The real failure mode is a crash/restart, which Cloud Run recovers from automatically.
- The pull model handles ALL failure modes: app was down during webhook, webhook delivery failed, webhook signature expired. On login, the state is always fresh.
- No Cloud Tasks, no Pub/Sub, no webhook signature verification infrastructure. Zero additional cost.

**What needs to be added to `share_grants`:**
```sql
ALTER TABLE share_grants
    ADD COLUMN IF NOT EXISTS pending_email TEXT,  -- set when user_sub is unknown at share time
    ADD COLUMN IF NOT EXISTS user_sub      TEXT;  -- nullable until pending grant is activated
```
(Currently `subject` stores the Permify subject string; `user_sub` is the Clerk sub extracted from it. This separation makes pending email lookup simple.)

**The notification email:** The sharer's intent is wasted if Alice never knows she was shared with. Two options:
- Clerk organization invitation (creates a Clerk-branded email) — ties CortexDrive to Clerk's org model, not ideal for cross-org sharing
- Transactional email via Resend/SendGrid (recommended) — full control over the email content, CortexDrive branding, direct link to the shared graph or sign-up page

Decision: transactional email. Keep Clerk for auth only, not for invitation delivery.

**Webhook as future fast-path (deferred):** When the platform is more mature and cost is less of a constraint, add Clerk webhooks as an optimization — provisions grants immediately on signup without waiting for the first login. The pull model stays in place as the reliable fallback. This is the standard "push-with-pull-fallback" reliability pattern.

## 4. Architecture Discussion — Depth Selector for Multi-Root Graph Shares

### Problem

For single-node sharing from the Bento panel (`POST /api/share/user`, `POST /api/share/group`), the BFS from a single root node with a single depth value makes sense. But when sharing a canvas with multiple root nodes (e.g., a cross-domain query returns both career nodes and podcast nodes), a single depth value can't be meaningfully applied to all roots.

### Decision: No Per-Root Depth for Graph Island Sharing

**For `POST /api/share/graph-island`:** No depth concept applies. You share exactly what's currently on the canvas — the pixel-level truth of what the user sees. The canvas IS already the result of a depth-bounded BFS traversal (the query that produced it). The depth was already applied when building the graph. Asking for a second depth application on top of that is redundant and confusing.

**For single-node Bento sharing:** Single depth slider (default 5) is correct and stays as-is.

**Per-root depth control (deferred):** A UI that shows each detected root node with its own depth slider is complex and covers an edge case: "share this graph but at different depths from each root." This exists in theory but the practical use case is marginal — most graph island shares are driven by what's on screen, which already reflects the user's depth intent. Deferred with a note that it may surface as a request when the group management UI is built.

## 6. Email Infrastructure — Resend Setup Discussion

### What Resend is

Resend (resend.com) is a third-party transactional email SaaS. CortexDrive does not run
an email server. Instead, when the gateway needs to send an email (e.g., "You've been
shared with — sign in to view"), it makes an HTTP POST to Resend's API. Resend handles
all delivery infrastructure: DKIM signing, SPF reputation, bounce handling, retry logic,
delivery analytics.

This is the same model as Clerk (auth SaaS), Permify (authorization SaaS), and Upstash
Redis (cache SaaS). The pattern is consistent: CortexDrive delegates specialized
infrastructure concerns to purpose-built services rather than operating them.

### What the Resend API key does

The API key authenticates the gateway to Resend's API — it proves "this HTTP request is
coming from CortexDrive, not a stranger." Without it, Resend rejects the send request
with a 401. The key follows the same Secret Manager pattern as every other credential in
the system:

```bash
# Store the key (run once after getting API key from resend.com):
echo -n "re_abc123..." | gcloud secrets create RESEND_API_KEY \
  --data-file=- --replication-policy="automatic" --project=cortex-drive-496915

gcloud secrets add-iam-policy-binding RESEND_API_KEY \
  --member="serviceAccount:377406326936-compute@developer.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor" --project=cortex-drive-496915
```

Then `--set-secrets="RESEND_API_KEY=RESEND_API_KEY:latest"` added to
`scripts/build-deploy-gateway.sh`. Gateway reads `process.env.RESEND_API_KEY`.

### Verified sending domain — Microsoft 365 path

**Prerequisite decision:** Create a Microsoft 365 mailbox for `cortex-drive.com`
(e.g., `sangeetha@cortex-drive.com`). This makes `cortex-drive.com` an active,
DNS-verified domain with MX records, SPF, and Microsoft DKIM in place.

**After M365 setup, add Resend DKIM:**
Resend requires adding one DKIM TXT record to the domain's DNS:
```
resend._domainkey.cortex-drive.com  TXT  "v=DKIM1; k=rsa; p=<key>"
```

**These coexist without conflict.** Microsoft 365 and Resend use separate DKIM selectors
(`selector1._domainkey` / `selector2._domainkey` for M365;
`resend._domainkey` for Resend). The SPF record needs to include both:
```
v=spf1 include:spf.protection.outlook.com include:_spf.resend.com ~all
```

This is a standard dual-use DNS setup used by thousands of companies:
- Microsoft 365 owns the inbox (receiving, your personal work email)
- Resend owns transactional outbound (noreply@cortex-drive.com system emails)

Same domain, different DNS selectors, no conflict.

## 8. Settings/Sharing Management Page — Architecture Discussion

### Problem
After generating a public graph link, there was no way to retrieve the URL if you navigated away from the modal. The "Public Link" tab only shows the URL immediately after generation.

### First proposal: add existing links list to the modal Public Link tab
Rejected in favour of a dedicated settings page for enterprise completeness.

### Decision: `/settings/sharing` with 3 tabs

Rationale: Box, Notion, Confluence all have a central sharing management view separate from the sharing action itself. CortexDrive's sharing surfaces (public links, named user/group grants, pending invites) span two tables and multiple status states — they belong in a management page, not a modal.

**Tab structure:**

| Tab | Data source | MVP status |
|---|---|---|
| Public Links | `graph_share_links` | ✅ Built |
| Named Shares | `share_grants` (active, user+group) | ⏳ Next |
| Pending Invites | `share_grants` (pending) | ⏳ Next |

Groups (create/manage) stay at `/settings/groups` (separate concern — identity, not access).

**Critique summary** (why `/settings/links` was rejected, `/settings/sharing` chosen):
- "Links" implies only public links; hides user/group grants from the management view
- Three distinct share types need three tabs; a single "links" view would be incomplete
- Recipient-side view ("Shared with me") is missing and should be called out as a future tab
- Revoke notification via Resend (email to recipient on revoke) is a future hook, not blocking
- Audit depth (access log per grant, not just view_count) is a future compliance item

**Entry point:** Settings gear icon in dashboard sidebar footer → `/settings/sharing`
**Cross-link:** "Manage all links →" shortcut inside GraphShareModal Public Link tab after generation.

## 9. Public Graph-View Page — Bug Fixes and UX Improvements

### Bug: "Link unavailable" in incognito (params.token = undefined)

**Root cause:** In Next.js 15 App Router, dynamic route `params` is a Promise
when received as a prop in client components. `params.token` resolved to `undefined`
synchronously, so the gateway received `GET /api/share/graph-link/undefined` → 404.
Confirmed in Cloud Run logs: `GET 404 .../api/share/graph-link/undefined`.

**Fix:** Replaced prop-based `{ params }` with `useParams<{ token: string }>()` from
`next/navigation`. This is the correct hook for dynamic segments in client components
across Next.js 14 and 15. One-line change, TypeScript clean.

### Public view UX: Path A improvements

After the 404 was fixed, the graph loaded but was not useful:
- All node labels were hover-only (black dots at rest)
- Clicking a node showed a thin drawer: type, name, description, links only

**Labels fix:** At load time, inject `isBentoEligible: true` on every node from the
snapshot. `EnterpriseGraph` uses `showLabelAtRest = !!(isExpandable || isBentoEligible
|| isAnchor || isGrouper)`. Snapshot nodes carry none of those flags normally, so all
fell into the hover-only leaf category. Tagging them `isBentoEligible` makes all labels
visible at rest without changing `EnterpriseGraph` itself.

**SnapshotPanel (anonymous path):** Replaced the thin drawer with a proper panel:
- Type badge + name
- Full description
- **Neighbors section** — derived from snapshot edges (`links` array): finds all
  directly connected nodes in the snapshot, renders as clickable chips (type label +
  node name). Clicking a chip navigates to that node's panel — hop between nodes
  with zero API calls, purely from frozen data.
- Resource links with smart fallback labels (GitHub, LinkedIn, InfoQ, AWS, etc.) —
  mirrors `BentoDetailPanel`'s label logic for visual consistency
- Sign-up CTA embedded in panel: "Create free account" + "Sign in" buttons
- Footer bar: persistent "Read-only view · Sign in · Create account →" bar

**Authenticated path:** When a signed-in user opens the public link:
- Same Bento hydration as dashboard (`POST /api/get_node_details` with their JWT,
  stale-while-revalidate + abort-on-navigate pattern)
- Full `BentoDetailPanel` renders — career/podcast layout, technologies, guests, all
  relationship-derived data
- Thin indigo banner at top: "You're signed in — click any node for full details."
  with "Open Dashboard →" shortcut

### Theme: default light, toggle to dark

The original page was all-dark (`bg-[#080a0f]`) — out of sync with CortexDrive's
light-themed dashboard.

**Fix:**
- Default: light theme (`bg-slate-50`, white header with shadow, slate borders, dark
  text) — matches dashboard
- Moon/Sun toggle button in header switches to dark mode (`bg-[#080a0f]`, white/5
  borders, white text) and back
- `SnapshotPanel` is fully theme-aware: all background, text, border, chip, link card,
  and CTA colours adapt to `isDark` prop
- `BentoDetailPanel` stays dark (consistent with its appearance in the dashboard)
- `EnterpriseGraph` canvas is `backgroundColor: 'transparent'` — follows container
- Label pills are `rgba(255,255,255,0.7)` — legible on both light and dark backgrounds
