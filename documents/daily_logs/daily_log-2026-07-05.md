## 1. Bug Fixes — Squashed Before New Feature Work

Six pre-existing bugs identified and fixed in a single commit (`feature-frontend-secure-gateway`):

### Bug 1: ShareModal invisible in production (React Portal)

`position: fixed z-50` inside a `z-40 absolute` parent creates a bounded CSS stacking
context — the modal was clipped and invisible. Fixed by wrapping the return with
`ReactDOM.createPortal(..., document.body)` so the modal escapes to the top of the DOM.

**Files:** `cortex-chat-ui/components/ShareModal.tsx`

### Bug 2: `element_id` dead code — 5 locations in dashboard (dashboard/page.tsx)

`elementId()` is Neo4j's internal unstable identifier (changes across migrations).
Stable node identity is `node_id` (UUID set at ingestion via `ON CREATE SET`).
All 5 usages of `freshNode.element_id`, `seedDetails.element_id`, `rel.element_id`
replaced with the correct `node_id` / `target_id` fields.

**Files:** `cortex-chat-ui/app/dashboard/page.tsx` (lines 270, 326, 550, 571, 607)

### Bug 3: `elementId()` in Cypher queries — expert_tools.py

Same `elementId()` problem in the Python MCP server. Fixed in:
- `get_node_details`: `elementId(n) = $node_id` → `n.node_id = $node_id`; removed
  `elementId(n) AS element_id` from RETURN
- `expand_node_topology`: `elementId(node) = $node_id` → `node.node_id = $node_id`
- Fallback search: removed `element_id: elementId(node)` from collect map
- `_fragment_neighbor_aggregation`: `id: elementId(neighbor)` → `neighbor.node_id`;
  `target_id: elementId(neighbor)` → `neighbor.node_id`
- Main Details projection: removed `element_id: elementId(node)`

Note: `elementId(n) IN $allowed_ids` throughout the Permify whitelist security clause
is intentionally unchanged — Permify writes tuples using elementId at bootstrap time.

**Files:** `src/mcp_server/expert_tools.py`

### Bug 4: `shareUrl` wrong host

`req.get('host')` in the gateway returns `api.cortex-drive.com` (the gateway host),
not `app.cortex-drive.com` (the frontend). Guest share links were pointing to the API.
Fixed: `process.env.FRONTEND_URL || 'https://app.cortex-drive.com'`.

**Files:** `cortex-gateway/index.js:634`

## 2. Enterprise Sharing Architecture Research

### Research question
How to share a complete graph view (all visible nodes and edges from a query response)
with named individuals AND custom groups (hr-recruiters, hiring-managers, family-members)?
What do Netflix, Google, Microsoft, Meta do at enterprise scale for similar features?

### Key findings

**Option A (snapshot)** — Copy all node data to a share record. Stale immediately as
the graph grows. Wrong for a living knowledge graph.

**Option B (live Permify grants)** — Write one `shared_viewer` tuple per root node.
Permify's `parent.can_view` traversal follows live composition edges at query time.
New chunks ingested after the share are automatically visible. Correct.

**Enterprise parallels:**
| System | Pattern | Relevance |
|---|---|---|
| Google Drive | Shared Drive + group membership | Group-based structural access |
| Slack | Channels + User Groups | Named audience sets within org |
| Notion | Group shares | Page-level group access |
| Linear | Teams | Custom named groups within org |
| Okta / Auth0 | Groups as first-class subjects | Cross-org group membership |
| Google Zanzibar | `group:name#member @user` | Exact subject shape we use |

**Key architecture decision — Option B with group subjects:**
One `shared_viewer` tuple on each root node with subject `group:groupId#member`.
Permify schema already supports `@group#member` on `shared_viewer`. No schema changes
needed. All group members get access via a single tuple per shared node.

### Graph-defined audiences (explained)

A novel capability: group membership computed from a Cypher predicate over the knowledge
graph rather than a manually maintained list. Example: "all users with a `GUEST_ON`
edge to an episode" = automatic audience for a podcast episode share. The audience
grows/shrinks as the graph evolves without any manual group management. Deferred to
a later phase — requires a materialized view or event-driven cache invalidation strategy.

## 4. Graph Island Sharing — Full Implementation

### What was built

A "Share Graph" button in the canvas toolbar that captures all N currently visible
nodes and shares them with a named user (by email) or a custom group. Recipients
must sign in to CortexDrive — no anonymous graph sharing.

**Graph island** = all nodes visible on the canvas after a query response. Unlike
single-node Bento sharing (which uses BFS composition depth), graph island sharing
takes the exact set of nodes the user sees and grants access to each one explicitly.

### Why one tuple per node (not root-only)

Graph island selections are arbitrary. The canvas shows a flat set of nodes that may
come from multiple topological roots (e.g., a cross-domain bridge query returns career
AND podcast nodes). Not all nodes in the island are connected by composition edges.
Root-only + parent.can_view only works if there's a single composition root.
One tuple per node is correct, unambiguous, and avoids partial access bugs.

### Bugs found and fixed during implementation

Two additional bugs found in `permify_gateway.js` during exploration:

| Bug | Fix |
|---|---|
| `shareNodeWithUser` used `_post('/data', ...)` — wrong endpoint for v0.9+ relationship writes | Changed to `_post('/relationships/write', { tuples: [...] })` |
| `listViewableNodeIds` returned `data.entityIds \|\| []` — Permify v0.9+ returns `entity_ids` (snake_case) | Changed to `data.entity_ids \|\| []` |

The `entityIds` bug meant the dedup preview in `/api/share/infer` was always showing
zero already-accessible nodes (returned empty array silently).

Two additional bugs fixed in `ShareModal.tsx`:

| Bug | Fix |
|---|---|
| Person tab POST body used `{ node_id }` but gateway expects `{ rootNodeId }` | Changed key to `rootNodeId` |
| `revokeAccess` sent `{ node_id, subject, relation }` but gateway expects `{ grant_id }` | Changed to send `{ grant_id }` |
| `ActiveGrant` interface had field `user` but history rows return `subject` | Rewrote interface to match DB columns |
| Manage tab rendered `g.user.replace(...)` — `g.user` was always undefined | Fixed to `g.subject?.replace(...)` |
| Expiry display read `g.condition?.context?.expires_at` (OpenFGA format) | Changed to `g.expires_at` (DB column) |

Security fix in `/api/share/revoke`: graph-island grants have one tuple per node.
The old revoke endpoint only deleted the tuple on `root_node_id`, leaving all other
nodes accessible. Fixed: for `grant_type = 'graph_island'`, fan-out revocation across
all `child_node_ids`.
