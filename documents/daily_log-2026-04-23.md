## 🛠️ Root Cause Analysis (Brittleness Investigation)

- **Fix**: Injected `load_dotenv()` into all server entry points and the `ExpertTools` constructor.

    - *Source*: `documents/cortex_drive_future_architecture.md` (Lines 16, 37-47).

- **Goal State**: Unified "Zero-Trust" check in every tool: `MATCH (n {tenant_id: $tenant_id}) WHERE n.owner_id = $requesting_user_id OR EXISTS { (User {id: $requesting_user_id})-[:HAS_ACCESS]->(n) } OR n.tenant_id = 'SYSTEM'`.

### 3. Ingestion Classification Strategy
To support **Progressive Discovery**, ingestion must mandate the following tiers:

| Tier | Mapping (e.g., categories_and_projects.md) | `tenant_id` | Access Logic |
| :--- | :--- | :--- | :--- |
| **SYSTEM** | **Backbones**: Company, Role, Project, Category. | `'SYSTEM'` | Accessible to all within the Cortex ecosystem. |

### 4. Cross-Tenant Collaboration (`is_external`)
To maintain strict governance during sharing, the `HAS_ACCESS` relationship must differentiate between same-tenant and cross-tenant users:

- **Internal Access (`is_external: false`)**: 
    - *Scenario*: User A shares a private note with User B (both in `org_123`).
    - *Constraint*: Standard administrative policies apply.
- **Guest Access (`is_external: true`)**: 
    - *Scenario*: User A (`org_123`) shares a project landmark with Guest X (`org_999`).
    - *Constraint*: Triggers "External Audit" logging. Nodes are marked as "Externally Shared" in the UI. Guest access is restricted to `viewer` role by default.

  id: n.role, // We use the string "Founder" as a virtual ID

## 🏛️ Advanced Security & Narrative Logic (Refinement)

### 1. The "Zanzibar Hybrid" Model
To balance **Collaborative Ease** with **Strict Privacy**, we are implementing a Hybrid ReBAC model:
- **Recursive Inheritance (`HAS_ACCESS*0..2`)**: Access now flows from Parents to Children (e.g., Category -> Project -> Link). This eliminates the need for redundant tagging.
- **The STAR Narrative Firewall**: Inheritance **breaks** for the `PreparatoryNote` label. Even if a user has access to a Project, they *cannot* see the STAR notes unless they are the explicit `owner_id`.

### 2. Narrative Header Sanitization
The internal STAR framework (Situation/Task/Action/Result) is treated as **Internal Scaffolding**.
- **Implementation**: A regex-based sanitizer strips these headers at runtime.
- **Rationale**: The Chat UI and Bento panel should show professional, narrative-first content, hiding the organizational "Situation:" tags from the executive viewer.

### 3. Stop Button & Zombie Prevention
- **Implementation**: Added `AbortSignal` support to the `MCPClient` (Frontend) and a disconnect listener in the `Gateway` (Backend).
- **Behavior**: Clicking "Stop" in the UI instantly terminates the HTTP request. The Gateway detects the disconnect and halts the orchestration loop, preventing the LLM from making further tool calls.
- **MCP Safety**: Existing Neo4j queries finish their current atomic execution, but no new queries are spawned, effectively killing the "zombie" process.

What happens to the MCP Server?
When the Gateway stops the query, it stops calling the MCP server for new tools. However, if a tool (like search_enterprise_graph) is already running on the MCP server:

Neo4j Transaction: The Cypher query currently executing in Neo4j will continue to completion (usually a few hundred milliseconds).
Python Execution: The MCP server will finish that specific tool call and return the result to the Gateway.
The Cut-off: The Gateway receives that final result but discards it. It does NOT send it back to the LLM for further reasoning.
Result: The "zombie" process stops after the current atomic task is finished. The LLM doesn't "think" anymore, and no more Neo4j queries are spawned.


### 4. Autonomous Contextual Fusion
- **Change**: Removed the manual "Contextual Fusion" radio button from the Dashboard Sidebar.
- **Rationale**: The feature is now **Always-On** by default. 
- **Intent Detection**: The AI now autonomously decides when to trigger the "Meta-Type Bridge" logic based on query intent (e.g., "influence", "relationship", "connection"). This simplifies the executive experience while keeping the advanced discovery power intact.


## Technical Summary: Unified Identity Proxy & Zero-Trust Restoration

### 🏛️ Architecture: The Smart Multiplexing Gateway
We have successfully resolved the architectural regression where "High-Speed Bento" hydration was bypassing security. The system now uses a **Unified Identity Proxy** pattern:

1. **The Gateway (Port 4000)** acts as the central traffic controller.
2. **Smart Routing**:
    - **Discovery/Bento**: Requests to `/api/get_node_details` are proxied to the **Bento REST Server (Port 8000)** for sub-second performance.
    - **Orchestration/Reasoning**: Requests to the primary `/api` are proxied to the **MCP SSE Server (Port 8080)** for long-running LLM tasks.
3. **Identity Injection**: Every request (Bento or MCP) now passes through the Gateway's `authMiddleware`. It verifies the Clerk JWT and injects `x-tenant-id` and `x-user-id` into the headers.
4. **Zanzibar Hybrid Enforcement**: The Python `ExpertTools` class now uses a unified `_get_security_clause()` helper that enforces visibility based on `owner_id`, `SYSTEM`/`PUBLIC` tiers, and recursive `HAS_ACCESS` logic.

### 📡 System Detail: What is SSE?
**SSE (Server-Sent Events)** is the backbone of the CortexDrive reasoning engine. 
- Unlike standard REST (one request, one response), SSE maintains a persistent stream.
- This allows the AI to "broadcast" its multi-step tool calls, thoughts, and partial graph updates to the UI as they happen.
- **Why SSE?** It provides the responsiveness needed for complex autonomous discovery without the overhead of full duplex WebSockets.
